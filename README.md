# Budget

**Budget** — fullstack-платформа для управления личными финансами: счетами, категориями, транзакциями и дальнейшим развитием в сторону аналитики, бюджетирования и финансового планирования.

Проект собран как **monorepo**: backend и frontend находятся в одном репозитории и развиваются согласованно. Основной фокус текущей реализации — надёжный backend с понятной доменной моделью, контейнеризацией, миграциями БД и готовой основой для дальнейшего масштабирования.

---

## О проекте

Этот проект показывает не только умение написать CRUD, но и способность проектировать **реальную backend-систему** с нормальной инженерной базой:

- продуманная доменная модель для финансового сервиса;
- REST API с валидацией, фильтрацией и пагинацией;
- JWT-аутентификация;
- миграции базы данных через Liquibase;
- Docker-based запуск окружения;
- OpenAPI-first подход к контрактам;
- интеграция frontend и backend в единый monorepo.

Иными словами, это не просто учебное приложение, а заготовка под полноценный продуктовый сервис.

---

## Что реализовано

### Backend

На текущем этапе backend покрывает базовый контур сервиса управления финансами:

- регистрация и аутентификация пользователей;
- работа с профилем пользователя;
- управление счетами;
- управление категориями доходов и расходов;
- создание, чтение и обновление транзакций;
- фильтрация транзакций по основным параметрам;
- offset-пагинация для списков;
- централизованная работа с миграциями базы данных;
- контейнеризированный запуск через Docker Compose.

### Frontend

Frontend вынесен в отдельную директорию внутри этого же репозитория и подключён как часть общего fullstack-решения. Это позволяет развивать клиентскую и серверную части в одной кодовой базе, не теряя связность проекта.

## Архитектура репозитория

```text
budget/
├── backend/   # backend-часть проекта
└── frontend/  # frontend-часть проекта
```

### Backend

В backend-части собраны:

- Java/Spring-приложение;
- Maven-конфигурация;
- Docker-конфигурация;
- Liquibase changelog’и;
- основной сервисный модуль.

### Frontend

Frontend расположен отдельно, что делает структуру репозитория понятной и удобной:

- backend и frontend не смешаны;
- можно независимо развивать UI и API;
- monorepo остаётся читаемым и поддерживаемым.

## Предметная область

Проект моделирует базовые сущности финансового сервиса:

- **User** — пользователь системы;
- **Account** — счёт, к которому привязаны операции;
- **Category** — категория дохода или расхода;
- **Transaction** — финансовая операция.

В архитектуре также заложен задел на дальнейшее развитие в сторону:

- агрегатов;
- бюджетов;
- прогнозов;
- алертов;
- сценарного анализа.

Такой подход позволяет эволюционно развивать систему без переписывания базы проекта с нуля.

## API-подход

Проект строится как backend с явным API-контрактом и аккуратным разделением ответственности между слоями.

### Ключевые идеи

- DTO используются на границе API;
- доменная и бизнес-логика сосредоточена в сервисном слое;
- валидация входных данных выполняется на уровне запроса и сервиса;
- структура API ориентирована на предсказуемость и расширяемость;
- OpenAPI используется как основа для описания контракта.

Это важный момент для production-like систем: код организован не только чтобы работало, но и чтобы это можно было поддерживать.

## Инженерные решения

### Monorepo-подход

Backend и frontend объединены в единый репозиторий. Это удобно для:

- синхронной разработки продукта;
- согласованного versioning;
- общей документации;
- прозрачной структуры для команды.

### Контейнеризация

Проект можно запускать в Docker-окружении, что упрощает локальную разработку и делает setup воспроизводимым.

### Управление схемой БД через Liquibase

Изменения в структуре базы оформляются через миграции. Это делает развитие проекта контролируемым и ближе к реальной командной разработке.

### Безопасность

Используется JWT-аутентификация, что создаёт основу для защищённого доступа к API.

### Чистое разделение слоёв

В проекте прослеживается правильное разделение между:

- transport/API layer;
- service layer;
- persistence layer;
- domain model.

### Масштабируемая предметная модель

Архитектура не ограничивается только транзакциями: в проект уже заложено развитие в сторону финансовой аналитики и планирования.
