# Budget

**Budget** — fullstack-платформа для управления личными финансами: счетами, категориями, транзакциями и дальнейшим развитием в сторону аналитики, бюджетирования и финансового планирования.

Проект собран как **monorepo**: backend и frontend находятся в одном репозитории и развиваются согласованно. Основной фокус текущей реализации — надёжный backend с понятной доменной моделью, контейнеризацией, миграциями БД и готовой основой для дальнейшего масштабирования.

---

## О проекте

Этот проект показывает не только умение написать CRUD, но и способность проектировать **реальную backend-систему** с нормальной инженерной базой:

- продуманная доменная модель для финансового сервиса;
- REST API с валидацией, фильтрацией и пагинацией;
- JWT-аутентификация;
- миграции базы данных через Liquibase;
- Docker-based запуск окружения;
- OpenAPI-first подход к контрактам;
- интеграция frontend и backend в единый monorepo.

Иными словами, это не просто учебное приложение, а заготовка под полноценный продуктовый сервис.

---

## Что реализовано

### Backend

На текущем этапе backend покрывает базовый контур сервиса управления финансами:

- регистрация и аутентификация пользователей;
- работа с профилем пользователя;
- управление счетами;
- управление категориями доходов и расходов;
- создание, чтение и обновление транзакций;
- фильтрация транзакций по основным параметрам;
- offset-пагинация для списков;
- централизованная работа с миграциями базы данных;
- контейнеризированный запуск через Docker Compose.

### Frontend

Frontend вынесен в отдельную директорию внутри этого же репозитория и подключён как часть общего fullstack-решения. Это позволяет развивать клиентскую и серверную части в одной кодовой базе, не теряя связность проекта.

На текущем этапе в frontend реализовано:

- регистрация и вход в систему с JWT-аутентификацией;
- защита маршрутов через router guards;
- dashboard с финансовой статистикой (доходы, расходы, баланс);
- визуализация данных: линейный график динамики расходов по дням и круговая диаграмма расходов по категориям;
- управление счетами: создание, просмотр, редактирование;
- управление категориями доходов и расходов: создание, просмотр, редактирование;
- управление транзакциями: создание, просмотр, редактирование;
- интеграция с backend API через Axios;
- состояние приложения через Pinia с поддержкой persisted state.

## Архитектура репозитория

```text
budget/
├── backend/   # backend-часть проекта
└── frontend/  # frontend-часть проекта
```

### Backend

В backend-части собраны:

- Java/Spring-приложение;
- Maven-конфигурация;
- Docker-конфигурация;
- Liquibase changelog’и;
- основной сервисный модуль.

### Frontend

Frontend расположен отдельно, что делает структуру репозитория понятной и удобной:

- backend и frontend не смешаны;
- можно независимо развивать UI и API;
- monorepo остаётся читаемым и поддерживаемым.

## Предметная область

Проект моделирует базовые сущности финансового сервиса:

- **User** — пользователь системы;
- **Account** — счёт, к которому привязаны операции;
- **Category** — категория дохода или расхода;
- **Transaction** — финансовая операция.

В архитектуре также заложен задел на дальнейшее развитие в сторону:

- агрегатов;
- бюджетов;
- прогнозов;

- сценарного анализа.

Такой подход позволяет эволюционно развивать систему без переписывания базы проекта с нуля.

## API-подход

Проект строится как backend с явным API-контрактом и аккуратным разделением ответственности между слоями.

### Ключевые идеи

- DTO используются на границе API;
- доменная и бизнес-логика сосредоточена в сервисном слое;
- валидация входных данных выполняется на уровне запроса и сервиса;
- структура API ориентирована на предсказуемость и расширяемость;
- OpenAPI используется как основа для описания контракта.

Это важный момент для production-like систем: код организован не только чтобы работало, но и чтобы это можно было поддерживать.

## Инженерные решения

### Frontend

В frontend-части реализованы следующие инженерные решения:

**TypeScript и строгая типизация**

Весь код написан на TypeScript со строгой конфигурацией (`strict: true`, `vueShim: true`), что обеспечивает безопасность типов на этапе компиляции и снижает количество runtime-ошибок.

**Архитектура на основе Composition API**

Компоненты используют `<script setup lang="ts">` и Composition API, что даёт:

- более компактный и читаемый код;
- удобное переиспользование логики через composables;
- предсказуемую структуру компонентов.

**Слоистая архитектура**

Код организован по слоям ответственности:

- `pages/` — страницы-маршруты;
- `components/` — переиспользуемые UI-компоненты (графики, элементы списков);
- `composables/` — вынесенная бизнес-логика (аналитика транзакций);
- `services/` — слой интеграции с API (Axios);
- `stores/` — глобальное состояние (Pinia);
- `types/` — типы и интерфейсы;
- `router/` — маршруты и guards авторизации.

**Управление состоянием через Pinia**

Pinia используется для хранения авторизационных данных и состояния приложения. Плагин `pinia-plugin-persistedstate` обеспечивает сохранение состояния между перезагрузками страницы.

**Серверный кеш через TanStack Query**

TanStack Query (Vue Query) используется для управления серверным состоянием, кэширования запросов, обработки состояний загрузки и ошибок, что снижает потребность в ручном управлении запросами.

**Визуализация данных**

Chart.js с обёрткой vue-chartjs используется для построения интерактивных графиков на dashboard: линейная динамика расходов и круговая диаграмма по категориям.

**Валидация форм на клиенте**

Quasar-компоненты форм имеют встроенную валидацию входных данных с пользовательскими сообщениями об ошибках до отправки на сервер.



### Monorepo-подход

Backend и frontend объединены в единый репозиторий. Это удобно для:

- синхронной разработки продукта;
- согласованного versioning;
- общей документации;
- прозрачной структуры для команды.

### Контейнеризация

Проект можно запускать в Docker-окружении, что упрощает локальную разработку и делает setup воспроизводимым.

### Управление схемой БД через Liquibase

Изменения в структуре базы оформляются через миграции. Это делает развитие проекта контролируемым и ближе к реальной командной разработке.

### Безопасность

Используется JWT-аутентификация, что создаёт основу для защищённого доступа к API.

### Чистое разделение слоёв

В проекте прослеживается правильное разделение между:

- transport/API layer;
- service layer;
- persistence layer;
- domain model.

### Масштабируемая предметная модель

Архитектура не ограничивается только транзакциями: в проект уже заложено развитие в сторону финансовой аналитики и планирования.

## Запуск опубликованного Docker-образа

Backend-приложение собирается в CI через GitHub Actions и публикуется как Docker-образ в GitHub Container Registry:

```text
ghcr.io/p0lt3rg31st/budget-service:latest
```

Для локального запуска можно использовать отдельный compose-файл:

```text
backend/docker-compose.registry.yml
```

Он запускает backend не из локальной сборки через `build`, а из уже опубликованного образа через `image`.

### 1. Перейти в директорию backend

```bash
cd backend
```

### 2. Скачать опубликованный образ

```bash
docker pull ghcr.io/p0lt3rg31st/budget-service:latest
```

Если образ закрыт правами доступа, нужно предварительно выполнить вход в GitHub Container Registry:

```bash
docker login ghcr.io -u P0lt3rg31st
```

В качестве пароля используется не пароль от GitHub, а GitHub Personal Access Token с правом `read:packages`.

### 3. Запустить приложение и базу данных

```bash
docker compose -f docker-compose.registry.yml up -d
```

### 4. Проверить, что контейнеры запущены

```bash
docker ps
```

В списке контейнеров должны быть:

```text
budget-db
budget-service
```

Если backend-контейнер запущен и не находится в статусе `Restarting` или `Exited`, приложение поднялось корректно.

### 5. Остановить окружение

```bash
docker compose -f docker-compose.registry.yml down
```

Для удаления контейнеров и volume с данными PostgreSQL:

```bash
docker compose -f docker-compose.registry.yml down -v
```
